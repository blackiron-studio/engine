Blackiron engine · proposal 0.4 · 2026-09-03 · implemented

The compiled kernel

0.3 put the engine on iOS natively, but the whole engine still ran in the JavaScript interpreter. iOS does not allow a JIT for third-party apps, so tight per-frame loops there run several times slower than in a browser. 0.4 moves those loops into a small Rust library that is compiled to machine code on every native platform and to WebAssembly on the web, behind the same scene API. The script keeps the tree, the UI and the game rules; the kernel does the work that scales with sprite, tile and particle counts.

Shape

Godot's split, applied to Blackiron: a compiled core, scripted games, one thin host per platform.

game code (TypeScript)            ─ scenes, rules, UI, input
scene tree (TypeScript)           ─ nodes, transforms, draw order, culling of big things
    │  one command stream per frame: sprite, rect, glyph, batch, particles, pass
    ▼
kernel (Rust)                     ─ expands the stream into vertices and draw commands,
                                    owns retained batches (tile maps) and particle emitters
    │  vertex buffer + BEGIN/PASS/DRAW/END
    ▼
host renderer                     ─ Metal (iOS), WebGL2 (browser)

What the kernel owns

PieceBefore 0.4In 0.4
Sprite, rect and glyph quadsScript computed every corner and wrote 40 floats per quadScript writes one 17-word record; the kernel applies the transform and writes the vertices
Tile mapsScript resolved and drew every visible tile every frame, building autotile names as stringsA retained batch written once; one command per frame culls and draws it natively. Animated tiles are a second, small batch rebuilt only when a frame changes
ParticlesScript stepped and drew each particleEmitters live in the kernel; one command per frame steps and draws them
Draw callsScript tracked pass boundariesThe kernel emits the command list; hosts play it back unchanged

Sprite nodes still walk the tree in script, so a scene with thousands of individually moving sprites still pays for them there. That is the next step (a retained node table), not this one.

Results

The bench project (examples/bench): 120×80 autotiled tiles under a panning camera, 2000 moving sprites, three emitters at about 4500 live particles, three lights, bloom and HD text. iPhone 17 Pro simulator; "JIT off" launches JavaScriptCore the way it runs on a real device.

Under device conditions the frame went from 20.8 ms to 6.1 ms and the bench holds 60 FPS. With a JIT available the kernel neither helps nor hurts, which is expected: the compiled JavaScript was already close to native for this work. On the web the same Wasm build is active in every project; the browser pane in the desktop app throttles hidden tabs, so no web timings were recorded.

Protocol

The stream is a Float32Array the renderer fills each frame. Op codes and layouts live in src/kernel/protocol.ts and kernel/src/lib.rs, and a test checks that the Wasm build and the TypeScript reference produce identical vertices for the same stream.

OpWordsMeaning
BEGINclear, viewW, viewHStart a frame; the view size drives culling
PASSid, clearSwitch to world, light or overlay
TRANSFORMa b c d e fCurrent local-to-screen transform
SPRITEx y sx sy rot ox oy w h u0 v0 u1 v1 tint alpha flagsOne quad
RECTx y w h color alpha additiveA solid quad from the atlas's white pixel
GLYPHx y w h u0 v0 u1 v1 color alpha additiveA glyph from the glyph cache
BATCHid alpha tint cullX cullY cullW cullH flagsDraw a retained batch, culled in its own space
PARTICLESid dt emitting ex ey alpha snapStep an emitter and draw it
ENDFlush the last draw

Batches and emitters are created through direct calls (createBatch, batchData, createEmitter, burst). Batch memory is a typed array over kernel memory, so a tile map is written once with no copies. The kernel's output is the same vertex format and command list 0.3 hosts already consumed, so the Metal renderer only changed where it reads them from.

Where it runs

  • iOS: BlackironKernel.xcframework (static libraries for the simulator and devices) linked into every exported project. The JavaScript side sees kernel memory directly through no-copy typed arrays, and the Metal renderer reads vertices straight from the kernel.
  • Web: 40 KB of WebAssembly embedded in the bundle, instantiated at startup. ?kernel=ts switches to the reference kernel for comparison.
  • Tests and headless: the TypeScript reference, so bun test needs no Rust toolchain. The generated src/kernel/kernel.wasm.ts is committed.
bun kernel/build.ts        # cargo: Wasm → src/kernel/kernel.wasm.ts, static libs → kernel/dist/
blackiron export ios / run ios  # copies the XCFramework into the project

What changed for game code

Nothing that existing projects call. TileMap and ParticleEmitter use the kernel when the renderer has one and fall back to their 0.3 behaviour otherwise (Canvas 2D, the fake renderer). TileMap.set marks the batch dirty; editing data directly needs invalidate(). The FPS pill now shows total CPU time per frame, not only the draw phase.

Next

  • Retained node table. Move Node2D transforms into kernel-owned arrays so static scenery and y-sorted actors cost nothing in script. This is what makes thousands of individual sprites free.
  • Collision and paths. Tile collision and grid pathfinding on kernel-owned grids, for games with many moving bodies.
  • Rendering in the kernel with wgpu. One renderer for Metal, Vulkan, DirectX and WebGPU. The Swift host shrinks to window, input and lifecycle, and the Android host becomes a thin shell instead of a second renderer.
  • Android. The same kernel as a shared library plus a JavaScript engine with a JIT (V8), which makes the interpreter question moot there.
