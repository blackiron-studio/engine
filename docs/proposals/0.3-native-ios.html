How Godot does it

Godot is a C++ core that renders and talks to the operating system, and a scripting layer where the game lives. Exporting to iOS means compiling that core for the phone once, as an export template, and pairing it with the game's data and scripts inside an Xcode project.

Blackiron has the same two halves already. The engine and the games are TypeScript; the host is whatever runs them and draws for them. On the web that host is the browser, and 0.2 pushed every host-specific thing behind a Platform interface and a Renderer contract. 0.3 writes a second host, in Swift with Metal, and an export command that packages it with a game. The scripting layer stays TypeScript, unchanged.

Why not a web view. A wrapper like Capacitor would ship in days, but it puts a browser between the game and the GPU and makes the engine depend on WebKit's schedule and quirks. A native host is the engine on every platform, and it is the only path to Metal, GameController, the audio session and the app lifecycle without an intermediary.

The four pieces of the host

  • Runtime. JavaScriptCore, which ships in every iOS and needs no dependency. Inside an app it runs as an interpreter, since Apple allows just-in-time compilation only in WebKit. That is fine for per-frame scene work and is the main thing to measure early; boot-time art painting is avoided entirely by shipping the atlas prebaked with blackiron atlas.
  • Renderer. A Metal implementation of the same passes the WebGL2 backend runs: the scene target at native resolution, the light target, the overlay target, the bloom chain and the composite. The five GLSL shaders become five Metal functions. On the TypeScript side a new NativeRenderer backend builds each frame as one vertex buffer and a short command list, which the host reads without copying.
  • Platform. The 0.2 seam implemented with the app bundle for assets, the Documents folder for saves, CADisplayLink for frames, UIScreen scale for the pixel ratio, plus two additions the browser used to provide for free: glyph rasterisation through CoreText for the text cache, and safe-area insets for anchors.
  • Audio. The synth's musical logic (moods, sequencing, envelopes) stays in TypeScript. What moves behind an AudioBackend interface is voice synthesis and sample playback, implemented on iOS with AVAudioEngine source nodes. The web keeps WebAudio behind the same interface.

Input arrives from the host the same way pointer and key events arrive from the DOM today, so the action map, the touch controls, focus groups and gamepad bindings from 0.2 work unchanged.

The host protocol

The protocol is the deliverable that outlives the Swift code. Any language that can run JavaScript and draw triangles can implement it, which is how Android and desktop get their hosts in 0.4 without touching the engine. 

// Host → engine (called by the host each display refresh and on events)
__blackiron.frame(timeMs)
__blackiron.pointer(kind, id, x, y, type)      // down | move | up | cancel, in points
__blackiron.key(code, down)                    // the same KeyboardEvent.code names as the web
__blackiron.pad(index, buttons, axes)
__blackiron.resize(width, height, scale, safeInsets)
__blackiron.visibility(visible)

// Engine → host (a small object the host installs on the global before loading game.js)
host.now()
host.loadBytes(path) / host.loadImage(path)         // from the app bundle; RGBA out
host.storage.get(key) / set(key, value) / remove(key)
host.rasterizeGlyph(font, ch) → { bitmap, w, h, left, top, advance }
host.uploadAtlas(w, h, rgba) / host.uploadGlyphs(w, h, rgba)
host.submit(vertices: Float32Array, commands: Uint32Array, post: Float32Array)   // one call per frame
host.audio.voice(spec, atSeconds) / host.audio.sample(name, opts) / host.audio.setMuted(m)

// The frame the engine submits
vertices: 10 floats per vertex, identical to the WebGL2 batch layout
commands: BEGIN rgb | PASS world|light|overlay rgb | DRAW first count | END
post:     bloom, threshold, passes, vignette, tint, saturation, contrast, brightness, lut id, grain, scanlines, offset

Two consequences fall out of this. The engine's per-sprite cost on a phone is a few array writes, the same as on the web. And the whole TypeScript side can be tested headlessly against a fake host that decodes the command list, before any Swift exists.

Three small conventions make this work. A game's entry exports a main function instead of running at the top level, so one bundle serves both the web page and the native host. fonts in blackiron.json may name local TTF files, which the web build also serves. And an ios block carries the bundle identifier, orientation and minimum version. 

// blackiron.json
{
  "ios": { "bundleId": "com.example.wisphollow", "orientation": "landscape", "minVersion": "16.0", "icon": "icon" },
  "fonts": ["fonts/PixelifySans.ttf", "fonts/InstrumentSans.ttf"]
}

// src/main.ts
export default async function main(app: App) {
  app.input.map({ ... });
  app.scenes.change(new TitleScene());
}

blackiron run ios builds and launches on the booted simulator; the Metal renderer runs there too. Real-device builds go through Xcode's signing like any other app.

Scope

0.3 is

  • The host protocol, versioned and documented
  • NativeRenderer, the AudioBackend seam, glyph rasterisation and safe insets on Platform
  • The main entry convention and local font files
  • BlackironHost, a Swift package: JavaScriptCore runtime, Metal renderer, iOS platform, audio voices, input, lifecycle
  • The same package on macOS, used to iterate quickly and as a desktop build for free
  • blackiron export ios and blackiron run ios
  • The demo and starters exported and running on device

0.3 is not

  • Android, Windows or Linux hosts. They implement the same protocol in 0.4
  • App Store submission tooling beyond a signed archive
  • In-app purchases, Game Center, push notifications
  • A new renderer feature set; native draws exactly what 0.2 draws
  • Bit-identical audio; the synth's timbres are re-created, not ported

Definition of done

  • blackiron export ios on the demo and each starter produces an Xcode project that builds without edits.
  • Every game plays on an iPhone with touch, and with a paired gamepad, with no web view in the process.
  • Lights, bloom, LUT grading, HD text and the overlay match the web build on the same scene, judged by side-by-side captures.
  • Saves persist across launches; backgrounding pauses and resuming restores cleanly.
  • The web build still runs from the same source with no native code in the bundle.
  • The host protocol is documented well enough that a second host could be written from it alone.
  • The engine's tests cover the native renderer's command stream and the fake host.

Decisions

Each needs a yes before M0. A recommendation is given for all of them.

JavaScript runtime

JavaScriptCore, the system one

Zero dependencies, zero binary size, a Swift API, and Apple maintains it. Runs as an interpreter in apps, which is the thing M1 measures first.

AlternativeHermes, Meta's bytecode interpreter, is faster in the no-JIT case and adds a compile step and a large dependency. Kept as the fallback if the frame budget fails.
Host language

Swift and Metal for Apple platforms

The native toolchain, direct Metal, GameController and AVAudioEngine, and nothing to justify to App Review. The protocol, not the Swift, is the portable part.

AlternativeOne Rust host on wgpu for every platform at once. Attractive for 0.4; starting there would delay the first iPhone build by weeks.
Frame transport

One vertex buffer, one command list

The engine already builds frames this way for WebGL2. The host reads the typed arrays in place through the JavaScriptCore C API, so a 1,300-sprite frame costs one bridge call.

AlternativeA draw call per sprite across the bridge. Simpler to write, thousands of crossings per frame.
Boot

Prebaked atlas, no painting on device

blackiron export bakes the atlas with the existing headless painter and ships the PNG. The interpreter never runs the pixel loops.

AlternativePaint at boot as the web does. Seconds of launch time in an interpreter.
Entry convention

Games export a main function

The only source change games need. The web page and the native host both call it after the host is ready, which also removes top-level await from bundles.

AlternativeKeep top-level scripts and build two bundles. Two entry paths to keep in sync forever.
Audio

Voices native, music logic in TypeScript

Sequencing and moods stay where they are and are tested there. The host only synthesises a voice from a spec at a time and plays samples.

AlternativeReimplement WebAudio's graph in Swift. Far more surface than the synth uses.

After 0.3

  • 0.4 Every platform. A second host speaking the same protocol for Android, Windows and Linux, most likely one Rust codebase on wgpu with an embedded interpreter, plus blackiron export android, windows, linux. The macOS build from 0.3 becomes blackiron export macos.
  • 0.5 Store tooling. Archives and uploads, icons and screenshots generated by the engine, Game Center and achievements behind a platform seam.
  • Later. A compiled path for the engine itself if the interpreter ever becomes the limit, which the protocol keeps open.

Next step. Settle the six decisions. M0 starts on the engine side and needs no Xcode; the first Mac window with the demo in it comes at the end of M1.
